# Atmos — Development Workflow

**Status:** Agreed project workflow. This is process context, **not** an OpenSpec change or implementation plan.

## Roles and responsibilities

- **User / developer:** decides significant product and architecture choices, approves scope, and personally implements selected parts of the NestJS Backend to learn server-side architecture, Prisma, Redis and integrations. The exact manual tasks are chosen per feature, not predetermined for the entire project.
- **Context/documentation assistant:** consolidates discussions into `product.md`, `architecture.md`, `design-reference.md`, `decisions.md` and this workflow. It does **not** author feature-specific OpenSpec `spec.md`, `proposal.md`, `design.md` or `tasks.md` by default.
- **Dedicated specification/planning agent:** reads the above context, initializes/configures OpenSpec, decomposes the work into changes, and creates feature-specific OpenSpec artifacts according to installed OpenSpec conventions. Keeps frontend and backend specs separate; changes spanning both may cover both.
- **Implementation agent:** implements only tasks explicitly delegated to AI. For user-owned Backend tasks, it may explain concepts, answer questions, verify requirements, and review code but must not implement or rewrite those parts without explicit permission.
- **Review/verification:** validate plans against approved requirements before coding; after coding check actual behavior, builds/tests and conformance. Plan review is not equivalent to code review. A separate verification report may be produced when appropriate by the responsible agent.

## Source of truth and boundaries

1. `docs/product.md` — approved product behavior and MVP boundaries.
2. `docs/architecture.md` — approved system and security decisions.
3. `docs/design-reference.md` and the **actual approved Figma frames** — UI reference; Figma is authoritative for visual details it covers. Agent access should be read-only.
4. `docs/decisions.md` — approved/deferred/open decisions, to prevent accidental scope or architecture drift.
5. OpenSpec artifacts are **downstream outputs**, prepared by the dedicated agent; do not mistake these context documents for implementation-ready specs.

If two sources appear inconsistent, flag the conflict before implementing. Do not present open design details or illustrative endpoints/schemas as approved final contracts.

## OpenSpec lifecycle

- Adopt **OpenSpec from project inception**, using its current supported structure and workflows rather than a custom incompatible format.
- The dedicated agent creates a change when an actual unit of work is ready. It prepares and reviews proposal/specifications/design/tasks as appropriate to current OpenSpec conventions.
- **Frontend and Backend requirements are documented separately** (with shared contract concerns addressed when needed); a cross-cutting change may update both.
- Assign each implementation task to **MANUAL** or **AI** before coding. Ownership labels are a local project convention, not a built-in OpenSpec feature.
- Review/approve the plan, implement incrementally, verify behavior and archive/update canonical OpenSpec specs at the proper lifecycle stage.
- Minor edits need proportionate process, not unnecessary ceremony; consequential architectural, security, product or scope changes require explicit approval and updated context documentation.

## Development order (direction, not a detailed task plan)

- First: repository foundation (pnpm workspaces, Turborepo, Docker Compose, React/Vite, NestJS, shared contracts setup, configuration), following a change authored by the dedicated agent.
- First functional vertical slice: search location, retrieve real weather via NestJS/Open-Meteo, and expose it through a minimal React integration. Redis weather caching is deferred to a later OpenSpec change under `WAPI-BE-DEC-001`.
- Subsequent capabilities: Overview completion, historical analytics, authentication, favorites/preferences, and MVP validation. The dedicated agent defines actionable sequencing and dependencies when each change is prepared.
- Only the first three initial API endpoints are presently in scope for detailed near-term design: `/api/health`, `/api/locations/search`, `/api/weather`. Other contracts should be specified only when their feature is being implemented.

## Engineering constraints already agreed

- Backend functionality chosen for learning is **implemented by the user**, not silently generated by AI.
- Frontend implementation follows approved Figma designs where available; no fabricated provider weather data in production behavior.
- Docker locally from the outset; eventual cloud deployment, with provider choice deferred.
- Tests start small: basic Backend Jest checks and critical Playwright E2E scenarios; no default requirement to unit-test every Frontend component or reach a coverage percentage.
- Keep direct changes focused. No speculative libraries, additional architectural layers, or broad future API implementations without justification/approval.

## Before implementation

A dedicated agent should inspect the repository's actual state and the installed OpenSpec version before creating files. The context bundle intentionally does **not** contain `openspec/`, generated change artifacts, code scaffolding, or runnable commands tailored to an uninspected repository.
